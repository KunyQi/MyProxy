# 工作原理

MyProxy 的设计围绕一个分工：复杂的部分由部署者一次做完，日常使用的部分尽量简单。这篇文章从三个角色讲起，再沿着“配对一次、连接一次”的过程，说明每一步背后发生了什么。

## 三个角色

**部署者**准备服务器、证书和 Xray，把服务器地址写进统一入口，然后构建三个客户端。这是整个流程里唯一需要懂网络的一步。

**管理员**在管理后台为每个使用者创建账号、生成配对码，必要时撤销设备。部署者和管理员常常是同一个人。

**使用者**只拿到一个配对码。他不需要知道服务器地址、协议或端口，也接触不到任何管理员凭据。

## 控制面与数据面分开

MyProxy 把“谁能用、用什么配置”和“流量怎么走”拆成两件事。

控制面就是 MyProxy Server。它管理账号、配对码和设备凭据，把连接配置下发给客户端，记录按类别聚合的用量，也负责撤销设备和登记更新。控制面不转发任何代理流量。

数据面是 Xray。客户端拿到配置后，直接和你服务器上的 Xray 建立 VLESS + REALITY 连接，真正的流量只经过这条通道。服务端通过 3x-ui 适配器在 Xray 里管理用户；拥有数据面管理权限的部分和对外的 API 分开运行，两者只通过本机上受保护的通道通信。

对公网开放的只有设备 API。管理接口和管理网页只能经过私有通道（例如 SSH 隧道）访问，即使有人知道服务器地址，也看不到管理入口。

## 一次配对

管理员在后台创建用户之后，为他生成一个配对码。配对码默认一小时内有效，也可以选一天或七天。它的明文只在生成时显示一次，管理员复制后，需要通过安全的渠道交给对应的人。

使用者在客户端输入配对码，客户端用它向控制面换取这台设备专属的凭据，配对码的任务就完成了。之后的连接都使用设备凭据，它保存在这台设备上。管理员可以随时在后台撤销某一台设备；被撤销的设备无法再取得配置，需要新的配对码才能重新绑定。

## 一次连接

按下连接开关之后，客户端依次做四件事：

1. **取得配置。**向控制面请求这台设备的连接配置。网络或服务器暂时不可达时，可以使用上一次验证成功后缓存下来的配置。
2. **启动内核。**Windows 和 Linux 使用 Xray，Android 使用基于 Xray 的 libv2ray。
3. **接管流量。**Windows 和 Linux 设置系统代理，在改动之前先保存并校验原设置的备份；Android 建立系统 VPN。
4. **确认可用。**通过刚建立的隧道访问你自己服务器上的检测地址，只有拿到预期的回应，客户端才显示“已连接”。

断开时顺序反过来：先恢复系统代理，再停止内核。如果恢复出了问题，客户端会保留内核和恢复信息，留待之后重试，而不是留下一个被改坏的系统代理。

在 Linux 上，连接由后台的守护进程持有。命令行工具和托盘界面都只是通过本地控制通道操作它，所以关闭托盘界面并不会断开连接。

## 流量怎么走

客户端提供两种连接模式，使用者可以在主页随时切换。

**智能分流**是默认模式：国内网站直连，其余流量走代理。判断按固定的顺序进行。私网地址和 BT 流量最先被阻断；接着，国内域名直连，常见国际服务的域名走代理；剩下没有命中任何规则的域名，交给内置 DNS 解析。解析结果里只要有私网地址就阻断，有国外公网地址就走代理，只有全部是国内公网地址时才直连。

**全局代理**让所有网站统一走代理，私网地址和 BT 流量同样始终阻断。

为了让查询更快，DNS 分成国内和国际两组，组内并行查询并保留缓存。在一组用模拟的慢、快解析器做的测试里，八轮冷查询的中位数从串行的约 623 毫秒降到了并行的约 65 毫秒。这说明等待解析的时间缩短了，并不等于下载速度变快。完整的规则顺序、覆盖的服务和测试方法，见参考里的[网络选路与优化](../network-routing.md)。

## 怎样才算“已连接”

很多客户端只要内核启动成功就显示已连接，MyProxy 会多走一步：通过隧道访问你自己服务器上的检测地址，确认这条路真的能走通。默认情况下不依赖任何公共探测站。

部署者可以在统一入口里再配置最多四个备用检测地址，客户端会依次尝试。每个地址最多等待五秒，整轮最多二十秒；全部失败时，客户端不会确认连接。使用者也可以随时点“检测连接”，手动检查一次并看到当前延迟。

## 安全与隐私的边界

- 客户端用标准 HTTPS 访问控制面，校验服务器证书的链、有效期和主机名，不会自动跟随重定向。
- 使用者手里只有配对码和设备凭据；设备 API 不会返回任何管理凭据。
- 用量按类别聚合记录。管理后台可以看到设备的出口地址，保留多久由部署者决定。
- 自建减少了对第三方 VPN 服务商的信任，但隐私仍然取决于服务器本身的安全、凭据的管理和客户端的维护。默认的分流规则包含直连部分，实际哪些流量经过代理，由策略决定。

## 更新

新安装的客户端默认不检查更新。开启检查后，更新清单和安装包都必须通过签名与摘要校验；部署者没有配置自己的信任密钥时，客户端会拒绝任何更新。检查到新版本也不会自动安装，始终由使用者确认。

发布新版本时，部署者在管理后台的“发布指派”向导里完成签名和上传，并选择这个版本的指派范围，详见[图形化发布与指派](../release-publishing.md)。
